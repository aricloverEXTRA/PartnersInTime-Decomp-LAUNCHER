WHAT "NOT MATCHING YET" ACTUALLY MEANS
--------------------------------------

The build already produces a byte-identical European ROM
(SHA-1 ba4ec2f99b4f2e0047601552bccf00aa73e28701). The game therefore already
boots and plays exactly like the retail cartridge, including the parts listed
here.

For every range that has not been reconstructed yet, the linker substitutes the
*original native bytes* from the extracted ROM. That is why the output still
matches. So an entry below does NOT mean "this feature is broken" or "this
cannot be played". It means:

  * the code is not yet readable or editable as C, and
  * you cannot yet change its behaviour by editing source.

A module reaches 100% when every one of its code bytes comes from C/C++ instead
of original bytes. Overlay 21 (Hammer attack) is the only module at 100% today,
which proves the target is reachable.

KNOWN BLOCKERS
--------------

Compiler register allocation
  MWCC 2.0 build 72 at -O4,p picks different registers than the original build
  for a handful of functions. Six separate source shapes for GameColor_Invert
  all produced the same 14 instructions in the correct order, differing only in
  9 register assignments. Affected and still deferred: GameColor_Invert,
  MI_CpuFill8, PXI_IsCallbackReady, the OS lock helpers, several battle
  candidates. Per AGENTS.md these are recorded and left alone rather than
  brute-forced.

Frame-less 512-byte fill
  func_02036cdc zeroes 512 bytes with repeated stm. memset compiles to a veneer
  call and struct assignment creates a stack temporary. The exact aggregate
  layout is unknown.

memmove pair
  func_0202cc58 and func_0202cd2c are an unlinked forward/backward pair used by
  roughly 30 linked files. Their dispatch uses "sub pc, pc, r2, lsl #2" and a
  trailing "sub pc, pc, #8" pad, which no C construct produces. Hand assembly
  would not count as matching C.

Named data blocking a code range
  func_ov006_0207b088 is a verified-exact 4-byte stub that cannot be linked yet.
  Nine named data symbols (data_ov006_0207af38 .. data_ov006_0207b038) occupy
  the unlinked gap directly below it and are declared extern by linked ov006
  units. Claiming the function splits that gap, so two generated reference
  objects both define those symbols and the link fails with 9 Multiply-defined
  errors. Deleting the reference objects and regenerating does not help. The
  0x0207AF38-0x0207B088 data blob has to be reconstructed as a linked data unit
  first. Same pattern may block other functions that sit next to named data.

Tooling
  tools/relink_native.py --require-matching reports 0 differing bytes for all 41
  ARM9, overlay and ARM7 modules it completes, then fails on arm7_autoload_000
  with "linked module differs in 2 bytes". That path reads only config/eur/arm7
  and the base ROM and never touches the ARM9 build, so it is very likely a
  pre-existing workstation discrepancy. Not yet confirmed against a clean
  baseline.

  Roughly 40 stray *.d probe artifacts sit untracked in the repository root.


HOW TO UPDATE THIS FILE
-----------------------

  python tools/configure.py eur
  ninja objects
  ninja check
  pwsh -NoProfile -ExecutionPolicy Bypass -File .\tools\build_nds.ps1 -DisableDataMods
  Get-FileHash -Algorithm SHA1 .\PiT_eur.nds
  python tools/generate_progress.py

python build/analysis/overlay_remaining.py [ovNNN ...] recomputes the per-module
function counts, sizes and histograms above from the current metadata.
